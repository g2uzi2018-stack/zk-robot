# TI5 T170C 原始 CAN 协议与物理关节映射规范

版本：调查稿 v1.2（2026-08-23）
目标：不依赖 ROS、不链接官方 `.so`，使用自主 C++/Linux SocketCAN 控制本机 T170C。  
范围：本体一体化关节和傲意灵巧手；底盘、相机、六维力、IMU 不属于本文的关节 CAN 协议。

## 0. 结论与可信度标记

现有材料足够实现一个自主的常规位置驱动，包括：电机发现、位置/CSP 读取、Position CSP 控制、自然下垂后的驱动器边界接管、反馈解析、故障读取框架、软限位、平滑、共享轴仲裁和超时监控。它还不足以称为厂家完整协议，主要缺口是抱闸、通信掉线后的固件动作、所有普通查询的逐帧响应、各型号安全参数和 PT 完整切换流程。

本文使用以下标记，开发时不可忽略：

| 标记 | 含义 |
|---|---|
| **A 已确认** | 当前源码/二进制实现与实机日志相互印证，可进入正式驱动 |
| **B 官方定义** | 官方 SDK/文档定义明确，但本机尚未逐字节抓包验证 |
| **C 旧版定义** | 只在旧头文件或旧实现中出现，可能存在固件版本差异 |
| **D 待补齐** | 现有工程无法确定，禁止按猜测实现 |

自主驱动运行时不需要官方 `.so`。官方 SDK 只作为离线取证和台架比对样本。

### 0.1 v1.2 实机修订摘要

- `0x01` 不能再作为本机 T170C 的伺服使能：完整 Ti5Control 启动轨迹中没有该帧，当前 SDK 的 servo power on/off 枚举也没有 raw 线码映射。
- GUI 的 STOP 已确认发送 `DLC=1 [02]`，作用是进入运行模式 0；不能据此推断去使能、抱闸或释放转矩。
- `0x71` 已由 Ti5Control 二进制映射和启动轨迹确认是刹车状态读取请求，不是旧头文件所称的“8 字节控制模式”。
- 模式 0、故障 0 并不等于任意 `0x44` 都会被接受；目标必须位于驱动器 `0x1A/0x1B` 返回范围内。自然下垂的反馈位置允许略微越过该目标范围，最近的范围内目标可完成边界接管。
- node 17 `R_SHOULDER_R` 已用 `0x44` 完成小幅往返和范围外边界接管；当前装配和坐标约定下，负的电机角增量对应现场观察到的向外方向。
- 未使用额外 session-ready 初始化命令，头部和双臂 17 轴已从自然下垂恢复走廊完成同步回零并保持。

## 1. 本机物理 CAN 拓扑

### 1.1 最近实机扫描确认的接口分区

| Linux 接口 | 物理分区 | 实际物理电机数 | CAN ID | 证据等级 |
|---|---|---:|---|---|
| `can0` | 腰部 + 折叠/升降 | 5 | `1–5` | **A**，多次运行日志扫描确认 |
| `can1` | 头/颈部 | 3 | `30–32` | **A** |
| `can2` | 左臂 | 7 | `23–29` | **A** |
| `can3` | 右臂 | 7 | `16–22` | **A** |
| `can4` | 左傲意手 | 1 个手控制器 | `70` (`0x46`) | 配置存在，在线状态未确认 |
| `can5` | 右傲意手 | 1 个手控制器 | `60` (`0x3C`) | 配置存在，在线状态未确认 |

注意：Linux 的 `canX` 编号受适配器枚举和启动方式影响。以上是当前定制工程最近日志中的实机映射，不应永久硬编码为机器人型号的绝对属性。物理电机唯一键必须是 `(can_interface, can_id)`；启动时应只读发现并与期望拓扑比较。

日志把 `can0` 统计成“6 个电机”，是因为业务配置分别列出腰部 `[1,2]` 和腿部 `[5,4,3,2]`，ID 2 被列了两次。物理上仍只有 ID 1–5 五台电机。

### 1.2 CAN ID 到具体物理关节

#### `can0`：Fold & WAIST

| CAN ID | 官方物理关节名 | 中文含义 | 当前定制工程中的业务语义 | 编码器/减速比 | 约束 |
|---:|---|---|---|---|---|
| 1 | `WAIST_Y` | 腰部偏航 | `waist_yaw` | 双编码器，101:1 | 安全关键轴；确认抱闸前禁止通用退出路径自动失能 |
| 2 | `Fold_P3` | 第三折叠俯仰 | 同时作为 `waist_pitch` 和腿链 `SHOULDER 3_P` | 双编码器，101:1 | **同一物理轴被两个业务组共享，只允许一个目标所有者**；直接承载防坠风险 |
| 3 | `Fold_P2` | 第二折叠俯仰 | 腿链 `SHOULDER 2_P` | 双编码器，101:1 | 重力/折叠承载轴 |
| 4 | `Fold_P1` | 第一折叠俯仰 | 腿链 `SHOULDER 1_P` | 双编码器，101:1 | 重力/折叠承载轴 |
| 5 | `Fold_R` | 折叠机构滚转/外摆 | 腿链 `SHOULDER_R` | 双编码器，101:1 | 承载机构轴 |

当前定制腿部命令数组顺序是 `[ID5, ID4, ID3, ID2]`，即：

```text
leg[0] -> ID5 Fold_R  / SHOULDER_R
leg[1] -> ID4 Fold_P1 / SHOULDER 1_P
leg[2] -> ID3 Fold_P2 / SHOULDER 2_P
leg[3] -> ID2 Fold_P3 / SHOULDER 3_P（同时复用为腰部 Pitch）
```

#### `can1`：头/颈部

| CAN ID | 官方物理关节名 | 中文含义 | 双编码器 | 减速比 |
|---:|---|---|---|---:|
| 30 | `NECK_Y` | 头部偏航 | 是 | 101:1 |
| 31 | `NECK_P` | 头部俯仰 | 是 | 101:1 |
| 32 | `NECK_R` | 头部横滚 | 是 | 101:1 |

当前定制话题使用 R/P/Y 三分量，电机取分量顺序为 `[2,0,1]`，即 ID 30 取 Yaw、ID 31 取 Roll 槽、ID 32 取 Pitch 槽。这个业务槽映射不改变官方物理关节名；接入其他上层控制器时必须显式建立语义坐标转换。

#### 腰部、折叠和头部当前软件限位

| CAN ID | 当前业务限位 | 说明 |
|---:|---:|---|
| 1 | `[-90°, 90°]` | 腰部 Yaw |
| 2 | 腰部视角 `[-90°,90°]`；腿链视角 `[-80°,80°]` | 两套配置冲突时必须由当前模式的唯一所有者决定，不可同时钳位后分别发送 |

| 4 | `[-90°, 90°]` | Fold_P1 |

这些是当前 `retargeting_T170C.yaml` 的主机软件限位，不等于固件限位、机械硬限位或无碰撞工作空间。

### 1.3 执行器型号信息的边界

官方 T170C 文档只给出了分组型号，没有给出每个 ID 的精确型号分配：

- 头部：`CRA-RI30-40-PRO-101-2E-EC2`、`CRA-RI40-52-PRO-101-2E-EC1`
- 手臂：RI30-40、RI40-52、RI50-60、RI60-70 系列，均为 101、双编码器变体
- 腰部：`CRA-RI70-80-PRO-101-2E-EC-B2`
- 折叠：`CRA-RI110-145-PRO-2-101-B1`、`CRA-RI100-120-PRO-101-2E-EC-B2`

因此编码器类型和减速比可以按官方 YAML 建立初始配置，但每个 ID 的精确执行器型号、电流/转矩上限和抱闸类型仍需在线查询或铭牌确认。

## 2. 传输层协议

| 项目 | 规定 |
|---|---|
| 总线 | Classic CAN 2.0，非 CAN FD |
| 波特率 | `1,000,000 bit/s` |
| 帧 ID | 标准 11-bit ID |
| 请求 CAN ID | 目标电机 `motor_id` |
| 响应 CAN ID | 同一 `motor_id` |
| 普通多字节字段 | little-endian |
| 应用层校验 | 本体关节帧无额外 CRC/BCC，依赖 CAN 链路层 CRC |
| Socket API | Linux `PF_CAN / SOCK_RAW / CAN_RAW` |

推荐的 SocketCAN 接口设置：

```bash
ip link set can0 down
ip link set can0 type can bitrate 1000000 restart-ms 100
ip link set can0 up
```

驱动不得假定 `write()` 成功等于电机已执行。必须用对应 CAN ID 的新反馈、接收时间戳和错误状态确认链路仍然有效。

### 2.1 现有工程是否自动拉起 CAN

几套代码的行为不同：

| 工程 | 是否自动拉起 | 实际命令/范围 |
|---|---|---|
| 原厂 `Ti5ROBOT_PACKAGE` 的 `joint_manager` / `Ti5RobotControl.so` | **是** | SocketCAN 连接时先枚举接口；对要打开的通道调用 `can_do_stop()`，等待约 100 ms，调用 `can_set_bitrate()`，再调用 `can_do_start()`，然后才执行节点发现。不是通过 shell 调用 `ip`，而是链接 `libsocketcan` 通过 rtnetlink 配置内核接口 |
| 当前 `ti5_follow_arm` 本体控制器 | **是** | 检查 `can0`～`can12`；接口存在但未 UP 时执行 `sudo ip link set canX up type can bitrate 1000000`，然后等待约 500 ms。后续电机扫描列表实际是 `can0`～`can11` |
| 当前傲意手节点 | **否** | YAML 中 `can_auto_bringup: false`。若改为 true，则先执行 `ip link set canX down`，再执行 `ip link set canX up type can bitrate 1000000` |
| 搬箱 `robot_hw_demo` | **是** | `init_socketcan()` 初始化 `can0`～`can5`，每口执行等价于 `sudo ip link set canX down && sudo ip link set canX up type can bitrate 1000000` |
| 搬箱 `build/init_all_can.sh` | 不是最终启动 | 对 `can0`～`can7` 先以 1 Mbps 拉起、随后又置 DOWN；目的是留下“干净”的 DOWN 状态供程序重配 |

#### 2.1.1 原厂 T170C 的准确启动链

官方 T170C YAML 中 `type: 1` 表示 SocketCAN，`baud_rate: 1000` 的单位是 kbit/s。官方库在打开设备时再乘以 1000，因此最终配置是 `1,000,000 bit/s`，不是 1000 bit/s。

原厂库中 `SocketCanInterface::initCanInterface(channel, bitrate_bps)` 的等效顺序是：

```text
can_do_stop(canX)
sleep(约 100 ms)
can_set_bitrate(canX, 1000000)
can_do_start(canX)
```

对应的命令行语义为：

```bash
ip link set canX down
ip link set canX type can bitrate 1000000
ip link set canX up
```

之后 `Motor_CanGetNodeInfo()` 才开始节点发现。SocketCAN 模式参数为：最多 6 个 CAN 通道、T170C 配置中的最大应用 ID、`baud_rate=1000 kbit/s`、单次发现超时约 20 ms、设备类型 5（SocketCAN）。发现结果再按应答电机 ID 匹配到实际通道，不能把 YAML 的 `device_index/can_index` 直接等同于本机固定的 Linux `canX` 编号。

原厂首次初始化路径没有显式配置 sample point、SJW、`txqueuelen` 或 `restart-ms`；`resetDevice()` 恢复路径会调用 `can_set_restart_ms(canX, 100)`。因此 `restart-ms=100` 可以作为与原厂恢复行为一致的自主驱动策略，但不能声称它是首次启动的必需协议参数。

这一动作需要网络管理权限。原厂 `run_ti5_services.sh` 会给 `joint_manager` 设置：

```text
cap_net_admin,cap_net_raw+eip
```

实机上的官方 `joint_manager` 当前也确实具有这两个 file capabilities，所以普通用户启动时仍能在进程内把 DOWN 的 CAN 接口配置为 UP。若自主程序不使用 `sudo`，同样必须以 root 运行或为可执行文件赋予相应 capability。

官方 T170C 关节连接配置全部是 SocketCAN、1 Mbps、双编码器、减速比 101；逻辑设备分组为：左臂 ID 23–29=`device_index 0`，右臂 ID 16–22=`device_index 1`，腰/折叠/头 ID 1–5、30–32=`device_index 2`。这是软件逻辑分组；最近实机发现的 Linux 接口仍是 `can0:1–5`、`can1:30–32`、`can2:23–29`、`can3:16–22`。

当前本体控制器只显式指定 `bitrate=1000000`，没有在命令中指定 `restart-ms`、sample point、SJW 或 `txqueuelen`。2026-08-22 不同启动阶段在线读取到的共同状态和变化项为：

```text
bitrate     1000000
sample-point 0.750
restart-ms  曾观察到 0 和 100
txqueuelen  曾观察到 10 和 1000
state       ERROR-ACTIVE
```

其中只有 1 Mbps 可以确定来自程序命令；其余值会受先前启动程序和接口重配影响，不能作为固件协议常量，也不能说是 `ti5_follow_arm` 显式配置。程序内部使用 `sudo` 的方案要求免密 sudo 或已有认证；傲意手的无 `sudo` 自动拉起则要求进程拥有 root/CAP_NET_ADMIN。

自主驱动若希望启动结果完全确定，建议由 systemd/启动脚本统一配置，而不是在实时进程中调用 `system("sudo ip ...")`：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 restart-ms 100
sudo ip link set can0 txqueuelen 10
sudo ip link set can0 up
```

对实际使用的 `can1`～`can3` 同样配置；不控制 Fold/WAIST 时可以不打开 `can0` 的业务发送路径。`restart-ms=100` 和队列长度 10 只能作为自主部署策略，不能描述为厂家协议或恒定现场状态，最终仍应纳入 bus-off/延迟测试。运动测试入口不应仅因这些非协议字段不同而临时 down/up 全部本体 CAN。

## 3. 数值单位与换算

### 3.1 位置

官方 T170C YAML 把 ID 1–5、16–32 全部配置为双编码器。双编码器的 CAN 位置是输出端 18-bit 多圈计数：

```text
counts_per_output_rev = 262144 = 4 × 65536
raw_position = trunc(output_rad × 262144 / (2π))
output_rad   = raw_position × 2π / 262144
```

旧定制代码中的 `4 × 65536` 是双编码器输出端一圈计数，不是减速比 4。官方配置中的真实减速比是 101:1。

若以后接入单编码器型号，位置是电机端 16-bit/圈计数：

```text
raw_position = output_rad × gear_ratio × 65536 / (2π)
output_rad   = raw_position × 2π / (gear_ratio × 65536)
```

编码器模式必须作为每个物理电机的配置字段，不能根据 CAN ID 猜测。

### 3.2 速度、电流、加速度与其他量

| 量 | CAN 原始单位 | 输出侧换算/说明 | 可信度 |
|---|---|---|---|
| 电流 | mA | `A = raw / 1000.0` | **B**，官方 API/文档确认 |
| 速度 | `0.01 Hz`，电机轴 | `output_rad_s = raw × 2π / (100 × gear_ratio)` | **A/B** |
| 加速度 | `0.01 Hz/ms`，电机轴 | 需再除以减速比换到输出端 | **B** |
| 位置 | count | 双编码器按 262144 count/输出圈 | **A/B** |
| 电池电压 | `0.01 V` | `V = raw/100` | **B** |
| 母线电压 | V | 官方 API 对外直接给 V；raw 字段宽度仍需抓包 | **B/D** |
| 电机/PCB 温度 | °C | 普通查询 raw 字段宽度仍需抓包 | **B/D** |

当前 CSV 曾出现最大/最小电流 `±13487 mA`、绝对保护值 `17983 mA`，但它只覆盖少量 ID，且同一电机的 PID 和位置字段在不同导出中明显冲突。不得把这些值当成全机关节业务限流。

## 4. 普通关节 CAN 帧

### 4.1 普通写入帧

绝大多数设置命令使用：

```text
CAN_ID = motor_id
DLC    = 5
DATA   = CMD V0 V1 V2 V3
VALUE  = int32_le(V0,V1,V2,V3)
```

查询/简单动作一般使用 `DLC=1, DATA=[CMD]`。PT 模式例外，见第 7 节。

### 4.2 `0x08` 读取当前位置 — **A 已确认**

请求：

```text
CAN_ID=motor_id  DLC=1  DATA=08
```

响应：

```text
CAN_ID=motor_id  DLC=5
DATA=08 P0 P1 P2 P3
position_raw=int32_le(P0..P3)
```

当前解析器只接受标准的 DLC 5；其他长度不更新电机状态，应记录为异常原始帧。

### 4.3 `0x41` 查询 CSP — **A 已确认**

请求：

```text
CAN_ID=motor_id  DLC=1  DATA=41
```

响应没有命令回显：

```text
CAN_ID=motor_id  DLC=8
DATA=I0 I1 V0 V1 P0 P1 P2 P3
current_mA  = int16_le(I0,I1)
speed_raw   = int16_le(V0,V1)       // 0.01 Hz，电机轴
position_raw= int32_le(P0..P3)      // count
```

普通 CSP 帧没有事务号，也没有响应命令字。必须按 `(interface,id,rx_timestamp,current_mode)` 关联，不能只看 `DLC=8`。

### 4.4 `0x44` 位置 CSP — **A 已确认，当前主控制命令**

请求：

```text
CAN_ID=motor_id  DLC=5
DATA=44 P0 P1 P2 P3
target_position=int32_le(P0..P3)
```

响应与 `0x41` 完全相同，为 8 字节 CSP，不回显 `0x44`。

对本机双编码器电机：

```cpp
int32_t raw = static_cast<int32_t>(target_rad * 262144.0 / (2.0 * M_PI));
```

### 4.5 `0x42` 电流 CSP — **B 官方定义**

```text
请求：CAN_ID=motor_id, DLC=5, DATA=42 [target_mA:int32_le]
响应：8 字节普通 CSP
```

逐电机安全电流未补齐前不得开放给普通业务。

### 4.6 `0x43` 速度 CSP — **B 官方定义**

```text
请求：CAN_ID=motor_id, DLC=5, DATA=43 [speed_raw:int32_le]
响应：8 字节普通 CSP
speed_raw = output_rad_s × gear_ratio × 100 / (2π)
```

### 4.7 非 CSP 模式命令 — **A/C/D**

| CMD | 请求数据 | 作用 | 可信度/约束 |
|---:|---|---|---|
| `0x01` | `DLC=1 [01]` | 旧实现猜测为伺服使能 | **D/否定证据**；当前 SDK 无 power on/off 线码映射，Ti5Control 启动也未发送，禁止作为 enable 使用 |
| `0x02` | `DLC=1 [02]` | STOP，进入运行模式 0 | **A**；GUI 独立动作抓包确认；去使能、抱闸和转矩释放行为仍未知 |
| `0x0B` | `DLC=1 [0B]` | 清故障 | **A/B** |
| `0x1C` | `DLC=5 [1C current_mA:int32_le]` | 进入/保持电流模式并设置电流 | **A** 格式；缺逐轴限值 |

### 4.8 `0x59` CSP 上传/通信掉线保护 — **B 格式确认，动作待补齐**

```text
CAN_ID=motor_id
DLC=5
DATA=59 U0 U1 D0 D1
upload_period      = int16_le(U0,U1)

```

官方示例 `59 64 00 C8 00` 表示数值 100 和 200，但时间单位以及超时后是保持、速度归零、失能还是抱闸均未说明。未完成卸载台架测试前禁止自动写入。

### 4.9 CSP 接管与驱动器目标位置参数 — **A 实机确认**

node 24 的受控观察结果：

```text
真正断电冷启动：0x03 -> mode 0，0x0A -> fault 0
随后发送 0x1E 或 0x44：命令被忽略
运行一次 Ti5Control 初始化，再发送 0x02 STOP：0x03 仍为 mode 0
随后发送 0x1E：能够执行，0x03 变为 mode 8
同一已就绪会话中发送 0x44：能够执行并返回 CSP 反馈
该状态保持到下一次物理掉电
```

2026-08-23 的补充只读检查发现，上述 node 24 拒绝 `0x44(q0)` 时：

```text
当前位置 0x08 = -64340 counts（约 -1.54213 rad / -88.36°）
驱动器最小位置 0x1B = -61895 counts（约 -1.48353 rad / -85.00°）
当前位置比 0x1B 低 2445 counts（约 0.05860 rad / 3.36°）
同位置 0x44(q0) 无 CSP 回传，模式保持 0，故障为 0
```

同一时刻，其余头部和双臂 16 个节点都位于各自 `0x1A/0x1B` 范围内，并连续接受三次同位置 `0x44(q0)`；node 24 是唯一同时“超出驱动器返回的目标参数范围”和“不接受 CSP”的节点。稍后 node 24 在下一次验收启动前的位置已经变为 `-1.39777 rad`，位置变化原因未由 CAN 日志唯一确定；进入 `0x1A/0x1B` 范围后，它成功完成 `+0.01 rad -> q0`，回零误差约 `0.000935 rad`，模式变为 8，故障仍为 0。

左肩横滚的安装换算为 `motor_rad = model_q - π/2`。因此最初的 `motor=-88.36°` 对应 `model≈+1.64°`，与现场观察到的双臂自然下垂、左右对称一致。`0x1A/0x1B` 在这里应称为驱动器返回的最大/最小目标位置参数；虽然其数值与命令是否被接受高度相关，但尚未证明它等同于机械安全限位。

2026-08-23 又完成了两组受控探针：

```text
left_shoulder_roll 当前 -1.431252 rad（-82.005°）：
  位于主机 ±80° 软限位外，但位于驱动器 -85° 最小目标内
  连续 30 次同位置 0x44：30/30 帧新反馈，mode 0 -> 8，fault 0
  最大位置变化 0 rad；随后 0x02 恢复 mode 0

right_shoulder_roll 当前 1.502966 rad（86.114°）：
  比驱动器 1.483527 rad（85°）最大目标高 0.019439 rad
  连续 30 次同位置 0x44：0/30 新反馈，mode 保持 0，fault 0
  改发边界内 1.478527 rad（84.713°）：100/100 帧新反馈，mode 0 -> 8
  最大位置变化 0.023633 rad，最大观测速度 0.088683 rad/s，fault 0
```

随后未发送 `0x01` 或任何参数写入，直接从该接管状态将头部和双臂 17 轴以五次曲线同步回到 CAN 电机角 0；全部进入 `0 ±0.012 rad` 并保持。因此已确认：`0x1A/0x1B` 是 `0x44` 目标的有效接管边界，不是反馈当前位置必须满足的机械边界；当前位置略微越界时，同位置目标会被忽略，但最近的范围内目标可以建立 CSP 并向内恢复。不需要额外的 session-ready 初始化命令来解释本次自然下垂后的拉起。

Ti5Control 的完整启动 trace 没有 `0x01`、系统控制、STOP、运行模式或目标写入；启动帧均能归入发现和参数读取。节点的第一类工厂接触帧是 `0x64` 电机类型发现/读取，但本次自主边界接管和完整回零没有依赖额外初始化帧，因此不再把 `0x64` 或未知会话触发器列为自然下垂恢复的必要条件。

自主驱动必须把“有位置反馈”“模式 0、故障 0”“当前位置”和“驱动器可接受的目标范围”分开处理。实机入口应读取 `0x1A/0x1B`：当前位置在范围内时，先连续发送当前位置 `0x44(q0)` 建立稳定反馈；当前位置因已标定的被动下垂略微越界时，只能在明确的恢复走廊和最大跨界距离内，先发送最近的范围内边界目标，验证反馈包络、速度、mode、fault 和最终位置后再单调向安全区恢复。任意未知越界姿态仍须拒绝。不得用 `0x01`、`0x70` 或 `0x71` 猜测性补齐初始化，也不得写参数绕过检查。

## 7. PT 力位混合模式

PT 是位置/速度误差反馈加前馈转矩的混合控制，不是普通位置模式。官方 SDK 的实时 PT 请求是没有命令字的 8 字节位打包帧，且不是 little-endian 整数字段：

```text
kp_u:      12 bit
kd_u:       9 bit
position_u:16 bit，通常映射 -12.5..+12.5 rad
speed_u:   12 bit，通常映射 -18..+18 rad/s
torque_u:  12 bit，范围由具体执行器配置

b0 = kp_u >> 7
b1 = ((kp_u & 0x7f) << 1) | ((kd_u >> 8) & 0x01)
b2 = kd_u & 0xff
b3 = position_u >> 8
b4 = position_u & 0xff
b5 = speed_u >> 4
b6 = ((speed_u & 0x0f) << 4) | ((torque_u >> 8) & 0x0f)
b7 = torque_u & 0xff
```

量化：

```text
u = round(clamp((x-min) × ((1<<bits)-1)/(max-min), 0, (1<<bits)-1))
```

观察到的反馈候选布局为：

```text
b0       状态/错误相关，准确语义待确认
b1..b2   position uint16 BE
b3,b4高  speed uint12
b4低,b5  current uint12
b6       线圈温度，候选换算 (byte-50)/2 °C
b7       PCB 温度，候选换算 (byte-50)/2 °C
```

PT 的以下信息仍缺失：完整进入/退出序列、反馈 b0、不同执行器的 Kp/Kd/转矩/电流边界、掉线恢复行为。旧头文件把 `0x71` 解释为 PT/轮廓切换，但当前本机线码已确认是刹车状态读取，因此不能再用它进入 PT。普通 CSP 和 PT 都使用同一 CAN ID、DLC=8，但布局不同，必须以每个电机的已确认模式状态选择解析器，不能写成“DLC=8 就按 CSP 解析”。当前正式驱动应禁用 PT。

## 8. 抱闸与 Fold/WAIST 约束

旧协议头文件定义：

```text
0x48, DLC=1：SET_BREAKE_OPEN，失能刹车/开闸
0x49, DLC=1：SET_BREAKE_LOCK，使能刹车/抱闸
```

这两个命令属于 **C 旧版定义**。官方 v2 系统命令枚举没有显式开闸/抱闸，只提供抽象的 `MOTOR_DEVICE_PARA_GET_BRAKE` 查询；该查询的本机 raw 请求已锁定为 `DLC=1 [71]`，但响应 DLC、0/1 极性以及“线圈命令状态还是机械到位状态”仍未确认。

当前两个工程的实际行为：

- 搬箱工程对 Fold/WAIST 使用 `0x1E` 位置命令，没有显式发送 `0x48/0x49`。
- 定制控制器未发现抱闸调用。腿部进入 hold 时排除腰部 ID `[1,2]`，实际向 `[5,4,3]` 批量发送 `0x02`。
- 搬箱工程的 SIGINT/SIGTERM 路径直接 `_exit()`，不发送退出安全帧。

这些事实可能表示驱动器固件自动管理制动器，也可能表示现场所谓“抱死”是伺服保持，不能据此作结论。协议补齐前的强制约束：

1. 生产路径不发送 `0x48/0x49`。
2. ID 1–5 默认不允许业务层自动发送 `0x02` STOP；其转矩和抱闸后果未验证。
3. ID 2–5 属于折叠承载轴；通信故障时优先停止更新目标并保持最后安全位置，不能未经验证直接失能。
4. 软件位置保持无法覆盖主机掉电，最终防坠必须由已确认的机械抱闸/STO/安全继电器承担。

## 9. 傲意灵巧手 CAN 协议

傲意手不是本体电机协议。其应用包结构为：

```text
55 AA HAND_ID 01 CMD LEN PAYLOAD... LRC
```

- `01` 为主站 ID
- `LRC` 是从 `HAND_ID` 到最后一个 payload 字节的逐字节 XOR。
- 完整应用包按每 8 字节切成多个 Classic CAN 帧，所有分片使用 `HAND_ID` 作为 CAN ID。
- 接收端按字节流重组；看到 `55 AA` 后根据 `LEN` 判断完整包长度。
- 协议没有 ISO-TP 序号或流控，同 ID 分片不能被其他发送者插入。

主要命令：

| CMD | 含义 | payload |
|---:|---|---|
| `0x50` | 六路手指/拇指位置 | 每路 `[position_u16_le, speed_u8]`，6 路共 18 字节 |
| `0x5F` | 查询状态 | `[0x80]` |
| `0x46` | 单路电流限制 | `[finger_id, limit_u16_le]` |
| `0x47` | 单路力限制 | `[finger_id, limit_u16_le]` |

状态 payload 至少 18 字节时，当前代码按每 3 字节读取一路位置的前两字节；达到 24 字节时，最后 6 字节为六路力值。当前配置控制频率 50 Hz、查询频率 20 Hz。左右手接口/ID 尚未用本次在线日志确认，因此启动时必须独立探测，且不要把本体关节的 `0x44` 等命令发送到手控制器。

## 10. 自主 C++ 驱动的开发约束

### 10.1 控制器唯一性

SocketCAN 允许多个进程同时打开同一接口。每个物理电机同一时刻只能有一个运动目标发布者：

- 使用全系统排他锁，例如 `/run/lock/ti5-can-controller.lock`。
- 启动前检查 `/proc/net/can/rcvlist_all`、`rcvlist_fil` 和已知控制进程。
- 发现其他控制器时拒绝进入运动态；不能只依靠“ROS 没启动”。
- 监听程序可以并存，但不得在相同 CAN ID 上发送查询或运动帧，除非由同一调度器管理。

### 10.2 ID 2 的唯一所有权

ID 2 不是两个电机。驱动内部只创建一个 `Motor` 对象，由模式仲裁器决定目标来源：

```text
NONE       -> 不接受运动目标
WAIST_MODE -> 只接受 waist_pitch
FOLD_MODE  -> 只接受 leg[3] / Fold_P3
```

切换所有者时必须停止旧目标、等待反馈稳定、用当前反馈作为新控制器首目标，再允许新目标变化。禁止两个业务线程各自向 ID 2 直接写 CAN。

### 10.3 坐标层次

CAN 位置只是电机/输出编码器坐标，不自动等于 URDF 关节角：

```text
业务/模型角
 -> 语义关节映射
 -> 方向符号
 -> 装配零偏/标定基线
 -> 机械与碰撞限位
 -> 电机输出角
 -> 编码器 count
 -> CAN 帧
```

当前左右臂重定向缩放和偏置是外骨骼到机器人业务坐标的配置，不应误当成电机原点标定。自主驱动应把 `direction`、`zero_offset_rad`、`encoder_type`、`gear_ratio`、软限位分别保存，并在实机逐轴确认。

补充核查显示，官方 T170C 控制链没有逐轴软件 `scale/offset`；官方 GUI 的 22 轴历史日志也能以 `raw_count×2π/262144` 直接还原动作目标。因此 CAN raw 到厂商电机角的当前配置统一使用 `direction=+1, zero_offset=0`。电机零点实际由驱动器内部的位置偏移承担。另有一层只供特定 IK/MDH 模型使用的 `motor_angle <-> model_q` 映射：T7/T170 左右臂及三折叠轴存在方向和 ±π/2 类偏置，详见同目录《TI5 T170C 现有标定与坐标映射核查》。这层模型映射不得重复填入 encoder calibration。

### 10.4 接收与事务模型

- 每个接口一个发送锁；同接口串行发送，不同接口可以并行。
- 一个集中接收线程使用 `poll()` 读取所有 CAN fd；查询函数不得直接抢 `read()`。
- 用 SocketCAN filter 只接收本接口期望的电机 ID 和错误帧。
- 所有接收状态带单调时钟时间戳和递增的本地主机序号。
- 普通 8 字节 CSP 无命令回显/事务号；不能靠请求—响应同步阻塞模型关联。
- 对异常 DLC、未知命令、未知错误位保留完整原始帧并计数。

### 10.5 自动发现

启动扫描只允许发送 `0x08`：

1. 枚举存在且已 UP 的 `canX`。
2. 清理接收缓存。
3. 对每个期望 ID 逐接口发送 `[0x08]`。
4. 50 ms 内只接受相同 ID、`DLC==5`、`data[0]==0x08` 的标准响应；其他长度保留为异常原始帧但不计入发现确认。
5. 连续确认 2–3 次才建立映射；当前原工程最大重试 5 次。
6. 同一 `(接口,ID)` 只创建一个物理电机对象。
7. 同一 ID 在多个接口响应并不天然冲突，因为接口是唯一键；但必须与预期分区核对。

自动分口、反馈缓存、平滑和限位都是主机应用功能，不是 ROS 框架或 CAN 总线自动提供的能力。

### 10.6 控制周期和总线调度

当前定制工程的参考值：

```text
控制/状态基准：100 Hz
同接口相邻电机发送间隔：50 us
一批发送后的反馈等待：200 us
发送累计失败阈值：30
```

官方测试曾使用更高频率，不代表整机生产推荐。自主驱动当前使用 50–100 Hz；同一周期用 `0x44` 已获得反馈时，不再额外发送 `0x08/0x41`。连续 2–3 个周期无新反馈时停止接受新轨迹并进入故障保持。

### 10.7 必须由自主代码实现的能力

| 能力 | 电机固件/CAN 是否自动提供 | 自主驱动责任 |
|---|---|---|
| 电流/速度/位置底层闭环 | 固件提供 | 选择模式、下发目标、监控反馈 |
| CAN 仲裁、ACK、链路 CRC | CAN 控制器提供 | 监控错误帧、bus-off 与重启 |
| 位置/速度等固件保护参数 | 固件可能提供 | 读取并核对；未经验证不写入 |
| 关节软限位和碰撞限制 | 不完整 | 必须实现 |
| 轨迹插值、速度/加速度/jerk 平滑 | 不提供 | 必须实现 |
| 自动分口 | 不提供 | 固定配置或只读扫描 |
| ID 2 共享轴仲裁 | 不提供 | 必须实现 |
| 反馈新鲜度、命令超时、重连 | 不完整 | 必须实现 |
| 抱闸/STO 防坠 | 当前不明确 | 软件只管理经过验证的接口，硬件承担最终安全 |

## 11. 当前正式实现边界

### 可以直接实现

- SocketCAN 接口配置、过滤、错误帧监控和统一接收线程。
- 用 `0x08` 发现 `(interface,id)`。
- `0x08` 位置读取、`0x41` CSP 查询。
- 使用 `0x44` 做双编码器位置 CSP 控制和 8 字节反馈解析；当前位置在驱动器目标范围内时，进入非零位移前先用 `0x44(q0)` 验证新反馈；已标定的被动下垂越界姿态先执行受限边界接管。
- 编码并显式请求 `0x02 STOP`，但接口只能命名为“请求 STOP 运行模式”；发送后必须查询 `0x03` 确认 `mode=0`，不得把它描述为去使能、释放转矩或抱闸动作。是否允许某个承载轴接收 STOP 由部件层安全策略决定，CAN/Motor 层不自动发送。
- 逐轴软件限位、最大单周期步长、速度/加速度轨迹限制。
- ID 2 唯一所有权、反馈超时、发送失败和 bus-off 状态机。
- `0x0A` raw 故障查询框架和已知位解析；在抓到响应后锁定最终帧格式。
- 正常控制只读电机参数并生成设备清单，不自动修改参数。
- 不实现或发送猜测性的 `0x01` enable。TI5 当前已确认的“开始位置控制”流程不是一条独立使能帧，而是在状态、故障、当前位置和目标范围检查通过后，以当前安全位置连续发送 `0x44(q0)`，获得稳定 CSP 新反馈并查询确认 `mode=8`；目标未被接受时禁止继续运动。

### 需要实验开关

- `0x42/0x43` CSP 电流/速度控制。
- `0x1C/0x1D/0x1E` 非 CSP 模式切换。
- `0x24/0x25` 速度限制写入。
- `0x59` 通信保护。
- 固件位置限位写入。
- 抱闸动作和任何去使能流程。

### 正式驱动默认不实现

- PT 力位模式。
- PID、CAN ID、波特率、电压、温度和编码器校准写入。
- Flash 保存、恢复出厂和 bootloader。
