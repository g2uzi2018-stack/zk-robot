# TI5 T170C 外骨骼串口协议与集成设计

## 0. 结论、适用范围与证据

本文件描述 `Qnbot_Exo_Plus` 外骨骼作为 TI5 T170C 主端输入设备时的串口协议，
并给出在本仓库中的建议集成边界。当前协议是**外骨骼到主机的连续上行数据流**；
本次调查没有发现主机必须向外骨骼发送的启动、查询或控制帧。

当前结论来自以下交叉证据：

1. 原遥操作工程的公开协议声明：
   `ti5_controller/include/ti5_controller/exo_protocol_parser.hpp`；
2. 原工程独立监测程序：
   `ti5_controller/scripts/exo_button_monitor.py`；
3. 原工程 `libti5_controller_lib.a` 中
   `exo_protocol_parser.cpp.o` 的符号和 ARM64 反汇编；
4. 在线设备的只读串口采样，131 字节帧的帧头、帧尾、长度和 XOR 校验均通过，
   且可稳定解释出双臂关节、摇杆、扳机和 IMU 数据。

原工程没有导出 `exo_protocol_parser.cpp` 和主控制器核心源码，因此凡是只由二进制
实现推断而来的细节，本文件会明确说明。协议拆包、字段偏移和当前实机格式已经由
在线帧确认；IMU 角速度的物理单位尚未得到独立资料确认。

### 0.1 当前在线设备

2026-08-28 在本开发机确认：

| 项目 | 值 |
|---|---|
| USB 产品名 | `Qnbot_Exo_Plus` |
| USB VID:PID | `0483:5740` |
| USB 序列号 | `397735593335`（仅当前这一台，换设备会变化） |
| 实际设备节点 | `/dev/ttyACM0` |
| 固定别名 | `/dev/exoskeleton -> /dev/ttyACM0` |
| 波特率 | `2,000,000` |
| 当前完整帧长度 | 131 字节 |
| 主机串口库 | 已安装 `libserial 1.0.0`，也可直接使用 POSIX `termios` |

USB 序列号不是协议字段，不应写死在协议解析器中；它只适合用于 udev 设备绑定。

## 1. 在本仓库中的层次

外骨骼是**输入设备**，不属于本体 CAN、Motor、Joint 或部件 Controller。建议分层为：

```text
Qnbot Exo Plus USB CDC
        |
        v
SerialTransport                 打开/关闭/read/poll，不理解业务字段
        |
        v
ExoskeletonStreamDecoder        字节流缓存、找帧头、整帧校验、失步重同步
        |
        v
ExoskeletonProtocol             小端字段解析、单位换算，不访问设备和线程
        |
        v
ExoskeletonState                双臂、摇杆、扳机、按键、IMU、时间戳
        |
        v
Retargeting / Motion            标定、限位、模式、安全门、轨迹生成
        |
        v
ArmController / HeadController  接收每周期已经规划好的目标
```

推荐后续文件位置：

```text
src/ti5/exoskeleton/exoskeleton_protocol.hpp/.cpp
src/ti5/exoskeleton/exoskeleton_stream_decoder.hpp/.cpp
src/ti5/exoskeleton/serial_transport.hpp/.cpp
src/ti5/exoskeleton/exoskeleton.hpp/.cpp
config/ti5/t170c/exoskeleton.yaml
tests/ti5_exoskeleton_protocol_test.cpp
tests/ti5_exoskeleton_stream_decoder_test.cpp
```

约束如下：

- `ExoskeletonProtocol` 必须是可离线单测的纯解析层；
- `ExoskeletonStreamDecoder` 处理拆包、粘包和噪声，不做重定向；
- `SerialTransport` 不拥有 Motion 或机器人 Controller；
- `Exoskeleton` 可管理连接状态和最新输入快照，但不直接下发本体 CAN；
- 读取线程不得直接调用 `ArmController::update()`；
- Motion/Executor 在自己的固定周期中消费带时间戳的最新有效输入；
- 串口掉线、数据过期或连续校验失败时，必须阻止新运动目标进入 Controller。

## 2. 串口与 USB 识别

### 2.1 串口参数

当前实机参数：

```text
baud:       2000000
data bits:  8
parity:     none
stop bits:  1
flow:       none
mode:       raw
direction:  外骨骼连续发送，主机读取
```

POSIX `termios` 可使用 `B2000000`。建议非阻塞打开串口并配合 `poll()`，而不是让
一个无期限阻塞的 `read()` 阻止退出和掉线恢复。串口打开后应清空**主机接收缓存**并
重新完成帧同步，但不应向设备发送未经确认的字节。

同一时刻只允许一个进程拥有外骨骼串口。建议沿用本仓库 CAN 控制唯一性的思路，
为外骨骼增加独立锁文件，例如 `/tmp/zk_robot_exoskeleton.lock`。

### 2.2 USB 匹配与 udev

默认严格匹配 `VID=0x0483, PID=0x5740`。固件版本变化可能导致 PID 变化；放宽为
仅匹配 VID 前，必须确保主机没有其它 STM32 虚拟串口，否则可能选错设备。

单设备 udev 示例：

```udev
SUBSYSTEM=="tty", KERNEL=="ttyACM*", \
  ATTRS{idVendor}=="0483", ATTRS{idProduct}=="5740", \
  SYMLINK+="exoskeleton", MODE="0660", GROUP="dialout"
```

多设备环境必须加入各设备的 `ATTRS{serial}` 并分配不同别名。不要让两台设备同时
竞争 `/dev/exoskeleton`。

## 3. 完整帧

### 3.1 当前 131 字节格式

```text
完整帧偏移 0       : 0xAA
完整帧偏移 1..128  : 128 字节 payload
完整帧偏移 129     : XOR 校验
完整帧偏移 130     : 0x55
```

校验只覆盖 payload，不包含帧头、校验字节和帧尾：

```cpp
std::uint8_t checksum = 0;
for (std::size_t index = 1; index <= 128; ++index)
{
    checksum = static_cast<std::uint8_t>(checksum ^ frame[index]);
}

valid = frame[0] == 0xAA &&
        frame[130] == 0x55 &&
        checksum == frame[129];
```

### 3.2 兼容帧长度

原协议声明保留三个格式：

| 完整帧 | Payload | 内容 |
|---:|---:|---|
| 51 字节 | 48 字节 | 双侧手柄与双臂关节 |
| 91 字节 | 88 字节 | 基础数据 + 第一组 40 字节 IMU |
| 131 字节 | 128 字节 | 基础数据 + 躯干 IMU + 头部 IMU |

当前 `Qnbot_Exo_Plus` 在线设备使用 131 字节格式。第一版正式实现建议通过配置固定
`frame_size: 131`，避免在任意噪声流中把一个偶然的短校验片段识别成旧帧。
只有确实需要旧硬件时，再把帧长作为启动时显式配置，不建议逐帧自动猜测。

原工程公开 `ExoProtocolParser::validateFrame()` 实际只验证旧的 51 字节格式；原主
控制器对 131 字节流另行完成同步和校验后，再调用 `parsePayload()`。后续新实现应
使用统一的“按配置帧长验证”，不能直接复制旧 `validateFrame()`。

## 4. 128 字节 Payload 字段

下表偏移均相对 payload；换算为完整帧偏移时全部加 1。所有多字节字段均为小端。

| Payload 偏移 | 长度 | 类型 | 含义 |
|---:|---:|---|---|
| 0 | 2 | `int16_le` | 左摇杆 X |
| 2 | 2 | `int16_le` | 左摇杆 Y |
| 4 | 1 | `uint8` | 左普通按键/档位原始字节 |
| 5 | 1 | `uint8` | 左拓展按键原始字节 |
| 6 | 2 | `int16_le` | 左扳机 |
| 8 | 2 | `int16_le` | 右摇杆 X |
| 10 | 2 | `int16_le` | 右摇杆 Y |
| 12 | 1 | `uint8` | 右普通按键/档位原始字节 |
| 13 | 1 | `uint8` | 右拓展按键原始字节 |
| 14 | 2 | `int16_le` | 右扳机 |
| 16 | 14 | `7 x int16_le` | 左臂 7 个关节编码器值 |
| 30 | 2 | `int16_le` | 左侧保留字，当前样本为 0 |
| 32 | 14 | `7 x int16_le` | 右臂 7 个关节编码器值 |
| 46 | 2 | `int16_le` | 右侧保留字，当前样本为 0 |
| 48 | 12 | `3 x float32_le` | 躯干 IMU 加速度 XYZ |
| 60 | 12 | `3 x float32_le` | 躯干 IMU 角速度 XYZ，物理单位待确认 |
| 72 | 16 | `4 x float32_le` | 躯干 IMU 四元数 WXYZ |
| 88 | 12 | `3 x float32_le` | 头部 IMU 加速度 XYZ |
| 100 | 12 | `3 x float32_le` | 头部 IMU 角速度 XYZ，物理单位待确认 |
| 112 | 16 | `4 x float32_le` | 头部 IMU 四元数 WXYZ |

不要把 payload 直接 `reinterpret_cast` 为未打包 C++ 结构体：这会引入对齐、别名、
宿主端序和未对齐访问问题。应使用逐字节小端读取或 `memcpy` 到固定宽度标量，并在
单测中覆盖负 `int16`、NaN、无穷值和非单位四元数。

## 5. 双臂关节

每侧占 16 字节，但只使用前 7 个 `int16`；最后一个字为保留字段：

```text
joint_rad = raw_int16 * (2 * pi / 16384)
```

即每个计数约为：

```text
0.0003834951969714103 rad
0.02197265625 deg
```

该值是外骨骼关节坐标，不是 T170C 电机输出角。进入本体 Controller 前至少还要经过：

1. 外骨骼到目标机器人关节的重定向；
2. 目标机器人模型关节限位；
3. Motion 轨迹连续性、速度和加速度约束；
4. 本仓库 `Joint` 层的模型关节到电机输出角转换；
5. 主机软件限位和驱动器 `0x1A/0x1B` 范围检查。

原 T170C 遥操作工程当前使用的初始重定向参数为：

```text
left scale   = [ 1, -1, -1, -1,  1,  1, -1]
left offset  = [-1.57, 0, 0, -1.57, 0, 0, 0] rad

right scale  = [ 1, -1, -1,  1,  1, -1, -1]
right offset = [ 1.57, 0, 0,  1.57, 0, 0, 0] rad

target_joint_rad = exo_joint_rad * scale + offset
```

对应关节顺序：

```text
0 SHOULDER_P
1 SHOULDER_R
2 SHOULDER_Y
3 ELBOW_Y
4 WRIST_P
5 WRIST_Y
6 WRIST_R
```

这些 scale/offset 是现场目标机器人标定，不属于串口协议。正式实现应放在配置和
Retargeting/Motion 层，不应写入协议解析器。与本仓库 `kinematics.yaml` 联调时必须
确认不会重复应用方向或零偏。

## 6. 摇杆与扳机

### 6.1 摇杆

当前解析算法：

```text
center = 2048
deadzone = 200

abs(raw - center) < deadzone  -> 0
其它                           -> (raw - 2048) / 1848
```

原实现没有在这个函数中强制限制到 `[-1, 1]`。提供给通用 Motion/底盘接口时，
建议在输入策略层显式 clamp，并保留 raw 值用于调试和标定。

### 6.2 扳机

主解析热路径的实际算法为：

```text
raw < 700       -> 0
raw > 3700      -> 1
700..3700       -> (raw - 700) / 3000
```

原静态库还保留了一个方向相反但未被 `parseJoystickData()` 调用的旧 helper；新实现
应遵循上面的实机热路径。原项目记录显示物理按满常约为 `0.96`，因此涉及夹爪闭合
阈值时应现场标定，不要假定每台设备都能稳定达到 1.0。

## 7. 普通按键、拓展按键与档位

两组按键均为**低电平有效**：相应位为 0 表示按下。

### 7.1 普通按键字节

| 位 | 掩码 | 含义 |
|---:|---:|---|
| 0 | `0x01` | 摇杆轴心按下 |
| 1 | `0x02` | 红键 / A |
| 2 | `0x04` | 蓝键 / B |
| 3 | `0x08` | 白键 / X |
| 4 | `0x10` | 黑键 / Y |

按键解析只检查低 5 位；高位还参与档位判断。原遥操作程序按完整原始字节定义：

| 左右普通字节组合 | 模式 |
|---|---|
| 左 `0x1F` 且右 `0x1F` | `BOTH_1F`，遥操作主模式 |
| 左 `0x3F` 且右 `0x3F` | `BOTH_3F`，退出遥操作/不控制 |
| 其它组合 | `NONE`，不一致或过渡状态 |

因此不能在保存模式字节前先做 `value & 0x1F`，否则会丢失 `1F/3F` 区别。
模式切换应经过保持时间、防抖和安全状态机，不能由单帧直接触发本体运动。

### 7.2 拓展按键字节

| 位 | 掩码 | 含义 |
|---:|---:|---|
| 0 | `0x01` | Back |
| 1 | `0x02` | Mode |
| 2 | `0x04` | Start |
| 3 | `0x08` | 后侧上键 |
| 4 | `0x10` | 后侧下键 |

普通键和拓展键都应同时保留 raw 与解析后的布尔值。无按键时低 5 位通常为
`0x1F`。

## 8. IMU

每组 IMU 为 10 个小端 `float32`：

```text
acc_x, acc_y, acc_z,
gyro_x, gyro_y, gyro_z,
quat_w, quat_x, quat_y, quat_z
```

原公开结构将加速度标为 `m/s^2`，但没有为角速度给出可信单位。第一版实现应将角速度
命名为 `angular_velocity_raw`，在获得固件或标定证据前不要标注 `rad/s` 或 `deg/s`。

四元数使用常规 WXYZ 顺序，原解析器用标准公式得到 roll/pitch/yaw，并输出角度。
新协议层建议同时保留原始四元数与标准 RPY，运行时统一使用弧度；用于腰和头之前，
再在 Retargeting 层处理设备轴语义、符号、基准和目标机器人轴映射。

原代码注释给出的设备语义为：

```text
设备 X 轴 -> Yaw
设备 Y 轴 -> Roll
设备 Z 轴 -> Pitch
```

这属于安装坐标语义，必须通过实际穿戴动作再次确认。头部 IMU 在某些在线帧中可以
全部为零；解析器应将“字段存在”和“数据有效”分开表达。

IMU 至少检查：

- 10 个浮点数均为 finite；
- 四元数范数在可接受范围内，必要时归一化；
- 全零四元数无效；
- 连接、换档或进入遥操作时建立明确基准；
- 失去新鲜帧时不得继续使用旧姿态生成新目标。

## 9. 流同步与连接握手

串口是连续字节流，一次 `read()` 不对应一帧。解码器必须支持：

- 半帧分多次读取；
- 一次读到多帧；
- 帧前噪声；
- 丢字节后重新同步；
- payload 内出现 `0xAA`；
- 校验或帧尾错误。

固定 131 字节模式的推荐算法：

```text
1. 把新字节追加到内部 buffer。
2. 查找第一个 0xAA；丢弃它之前的噪声。
3. 不足 131 字节则等待下次 read。
4. 检查候选字节 130 是否为 0x55。
5. 计算候选 payload 的 XOR 并比较字节 129。
6. 通过：消费 131 字节并输出一帧。
7. 失败：只丢弃当前第一个字节，然后重新查找 0xAA。
```

失败时只丢一个字节非常重要；不能因为 payload 内出现 `0xAA` 就提前截帧，也不能
整块清空可能包含下一帧头的缓存。

原工程连接握手参数可作为初始参考：

```text
handshake_valid_frames: 3
handshake_timeout_sec: 2.0
device_scan_interval_sec: 1.0
```

即只有在限定时间内收到至少 3 个合法完整帧，连接才进入 Ready。正式实现还应记录：

```text
received_bytes
valid_frames
checksum_failures
tail_failures
discarded_bytes
last_valid_frame_time
reconnect_count
```

## 10. 建议 C++ 数据模型

协议层应使用固定尺寸容器并保留 raw 值：

```cpp
namespace robot::ti5::exoskeleton
{

struct JoystickState
{
    std::int16_t raw_x{0};
    std::int16_t raw_y{0};
    double x{0.0};
    double y{0.0};
    std::int16_t trigger_raw{0};
    double trigger{0.0};
    std::uint8_t buttons_raw{0};
    std::uint8_t extended_buttons_raw{0};
};

struct ImuState
{
    std::array<float, 3> acceleration{};
    std::array<float, 3> angular_velocity_raw{};
    std::array<float, 4> quaternion_wxyz{};
    bool present{false};
    bool valid{false};
};

struct ExoskeletonFrame
{
    std::array<double, 7> left_joint_rad{};
    std::array<double, 7> right_joint_rad{};
    JoystickState left;
    JoystickState right;
    ImuState torso_imu;
    ImuState head_imu;
    std::uint8_t left_mode_raw{0};
    std::uint8_t right_mode_raw{0};
};

} // namespace robot::ti5::exoskeleton
```

传输/设备层再附加主机单调时钟时间戳和连接序号，不建议把时间戳伪装成串口 payload
字段。

有限数值，不能静默补齐 7 关节数组。

## 12. 安全状态机

串口帧合法不等于允许控制。建议至少区分：

```text
Disconnected
  -> Synchronizing       已打开串口，尚未通过连续合法帧握手
  -> Ready               数据有效，但尚未授权机器人跟随
  -> TeleoperationArmed  模式、防抖、基准和本体准备均通过
  -> Running             Motion 按固定周期生成并下发目标
  -> Stale/Failed        掉线、过期、质量失败或本体错误
```

必须满足以下条件才允许进入 `Running`：

- 外骨骼连接 Ready，数据未过期；
- 连续合法帧和数据质量检查通过；
- 当前模式经过防抖确认；
- 双臂外骨骼基准和目标机器人初始位置已建立；
- 本体 `Arm::prepare()` 和当前位置接管已成功；
- Motion 首个目标等于或连续衔接当前实测位置；
- 操作者和现场承托条件满足实机测试要求。

以下事件必须立即停止生成新运动目标并进入 Stale/Failed：

- 串口关闭、poll 错误或重连；
- 最新合法帧超过新鲜度阈值；
- 连续校验失败超过阈值；
- 关节突变、非有限值或 IMU 质量失败；
- 本体 CAN、Motor、Joint、Controller 任一层失败；
- 两侧档位不一致或退出遥操作模式。

“停止生成新目标”不等价于实体机器人已安全停止。最终停止动作仍必须走本仓库已经
确认的部件停止与反馈确认路径，并遵守 `TI5_T170C_Controller层设计.md` 的约束。

## 13. 单元测试与联调顺序

### 13.1 不连接实体设备的自动测试

协议层至少覆盖：

- 已确认 131 字节样本能够解析；
- 51/91/131 各帧长的 XOR 边界；
- 错误帧头、帧尾和校验拒绝；
- 正负 `int16` 关节及小端换算；
- 7 关节 + 1 保留字不会错位；
- 普通键和拓展键低电平映射；
- `0x1F` 与 `0x3F` 模式不被低 5 位掩码混淆；
- 摇杆死区边界 1848/1849/2247/2248 等；
- 扳机 699/700/3700/3701 边界；
- IMU float 小端、NaN、Inf、全零四元数；
- buffer 按 1 字节、随机块、多帧粘连方式输入结果一致；
- 噪声、截断帧、错误候选后可恢复下一合法帧。

### 13.2 只读实机测试

第一阶段工具只打开外骨骼，不启动本体 CAN 运动：

1. 打印 USB/串口识别信息；
2. 完成连续合法帧握手；
3. 显示接收频率和错误计数；
4. 分别活动每个外骨骼关节，确认索引、方向和连续性；
5. 测试摇杆、扳机、普通键、拓展键和 `1F/3F` 档位；
6. 单独验证躯干、头部 IMU 轴语义和基准；
7. 记录一段原始二进制数据作为回归 fixture。

### 13.3 仿真/无动力联调

只把外骨骼输入送入 Retargeting 和 Motion，输出目标日志或仿真模型，不调用实体
Controller。确认零位、方向、关节名、限位和首帧连续性后，才进入受控实体联调。

### 13.4 实体机器人联调

按单臂、低速、小范围、可承托的顺序开始。任何协议、方向、零偏或停止行为未确认时，
不得直接启用双臂全范围跟随。

## 15. 当前已知边界与待确认项

已确认：

- 当前设备 USB 身份、2 Mbps 串口和 131 字节帧；
- `0xAA` 帧头、`0x55` 帧尾和 payload XOR；
- 双侧手柄、7+7 关节、两组 IMU 的偏移与小端；
- 关节计数到弧度换算；
- 摇杆和主热路径扳机换算；
- 普通/拓展按键低电平映射；
- `0x1F/0x3F` 模式原始字节语义；
- 原 T170C 工程使用的重定向参数。

仍需在正式实现前或联调阶段确认：

- 固件是否存在必须由主机发送的隐藏初始化帧；当前连续流不需要；
- IMU 角速度的物理单位；
- IMU 加速度是否已经换算为 `m/s^2`，在线静止模长更接近约 1，需核对是否实际为 g；
- 头部 IMU 全零的设备/连接条件；
- 不同外骨骼硬件或固件是否仍使用 131 字节；
- 实际持续发送频率、允许的新鲜度阈值和重连行为；
- T170C 重定向参数与本仓库 `kinematics.yaml` 的最终组合；
- 退出遥操作或串口掉线时，实体机器人最终采用哪条已验证停止流程。

在这些待确认项关闭前，外骨骼集成应保持 `enabled: false` 或只读模式，不应默认驱动
实体机器人。
