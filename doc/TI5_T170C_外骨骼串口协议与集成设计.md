# Qnbot 外骨骼（厂商 SDK v1.2）集成设计

## 0. 结论

本仓库把 Qnbot 外骨骼作为机器人输入设备接入。协议字段、帧长度、校验、原始手柄
值、按键位图和编码器换算，统一以随项目保存的厂商资料包
`qnbot-exoskeleton-SDK/qnbot_sdk_v1.2/` 为准，具体权威实现是：

- `qnbot_sdk.py`：`QnbotStreamParser`、`TelemetrySnapshot` 和 `QnbotClient`；
- `SDK使用说明.md` / `SDK_User_Guide.md`：字段和功能说明；
- 厂商 CLI：版本、能力、校准、无线、触觉和 DFU 操作。

仓库中的 C++ 代码只实现厂商 SDK 已定义的 legacy 遥测流子集，以便在 TIAGo 的固定
控制周期中使用；需要 QnTP 请求/响应或设备维护时使用厂商 Python SDK。C++ 不再保留
与 SDK 冲突的旧模式值、旧归一化常量、旧关节数量假设或旧协议字段。

当前可运行的本体入口是 `tools/exoskeleton_tiago_teleop.cpp`，目标是 TIAGo 双臂、
双夹爪和底盘。TI5 目前只有外骨骼输入层，没有同等完整的 TI5 本体遥操作入口。

重要边界：厂商 SDK 只提供每侧 8 个编码器槽位和弧度换算，不提供“槽位对应人体哪根
骨骼/目标机器人哪根关节”的语义，也不提供 TIAGo 的零位、方向和限位映射。因此，
外骨骼数据转换为实际机器人姿态必须经过现场逐轴标定；未标定时禁止实体控制。

## 1. 分层和文件

```text

      |
      v

      |

      |
      v

      |
      v

```

对应文件：


`ExoskeletonProtocol` 不访问设备、不启动线程、不生成机器人目标；`Exoskeleton` 只
负责连接、重连、最新合法快照和新鲜度。读取线程不能直接调用机器人 Controller。

## 2. 厂商协议范围

### 2.1 Legacy 遥测流

厂商 SDK 定义：

```text
帧头 SOF       = 0xAA
帧尾 EOF       = 0x55
校验           = payload 全部字节逐字节 XOR
```

支持的 payload 和完整帧长度如下：

| SDK `format_version` | Payload | 完整帧 | 内容 |
|---:|---:|---:|---|
| 1 | 48 | 51 | 双侧手柄 + 双侧 8 个编码器 |
| 2 | 88 | 91 | 版本 1 + 第一组 IMU |
| 3 | 128 | 131 | 版本 2 + 第二组 IMU |

完整帧布局是 `SOF + payload + XOR + EOF`。C++ 解码器支持固定 51/91/131 和 SDK
同样的 `auto` 模式；当前配置固定使用已确认的 131 字节格式。

`auto` 只是在三种厂商已定义长度中选择，不会猜测其它长度。校验失败时只丢弃当前
候选起点，继续查找下一个 `0xAA`，以支持半帧、粘包、噪声和断字节恢复。

### 2.2 QnTP 管理协议

厂商 SDK 同时定义 QnTP：`SOF=0xA5`、版本 1、8 字节头、CRC16-CCITT 和最多
4096 字节 payload。`QnbotClient` 用于 `System`、`DeviceProfile`、`Telemetry`、
`Encoder`、`Handset`、`IMU`、`Wireless`、`Haptics` 和 `DFU`。

本仓库没有在 C++ 控制周期中重复实现 QnTP 请求/响应。需要打开 legacy 流、读编码器
拓扑、读手柄校准或维护设备时，使用厂商 SDK 或 `tools/qnbot_vendor_probe.py`。
同一串口不能同时被 Python SDK、C++ 监测器和遥操作程序占用。

## 3. Legacy payload 字段

以下偏移均相对于 payload，所有多字节字段均为 little-endian；完整帧偏移需要加 1。
字段定义与厂商 `_parse_telemetry_payload()` 一致。

| Payload 偏移 | 长度 | SDK 字段/类型 | 含义 |
|---:|---:|---|---|
| 0 | 8 | `joystick_left: 4 x int16` | `[axis_x, axis_y, key_mask, trigger]` |
| 8 | 8 | `joystick_right: 4 x int16` | `[axis_x, axis_y, key_mask, trigger]` |
| 16 | 16 | `arm_joint_left: 8 x int16` | 左侧编码器原始槽位 |
| 32 | 16 | `arm_joint_right: 8 x int16` | 右侧编码器原始槽位 |
| 48 | 40 | `10 x float32` | 第一组 IMU，格式 2/3 存在 |
| 88 | 40 | `10 x float32` | 第二组 IMU，格式 3 存在 |

IMU 每组的 10 个值依次为：

```text
acc_x, acc_y, acc_z,
gyro_x, gyro_y, gyro_z,
quat_w, quat_x, quat_y, quat_z
```

C++ 使用逐字段读取，不把 payload 强制转换成未打包结构体。协议层保留 IMU 原始值，
并额外检查 float 是否 finite、四元数是否明显接近单位四元数；这些是本地数据质量
策略，不是新增的厂商协议字段。角速度物理单位和 IMU 到机器人姿态的轴语义尚未由
SDK 定义，不能直接拿来驱动 TIAGo 头部或腰部。

## 4. 手柄字段和 SDK 语义

### 4.1 原始轴值

`TelemetrySnapshot` 只给出原始 `axis_x`、`axis_y`、`trigger`。C++ 的
`JoystickState` 同样只保存：

```text
raw_x, raw_y, trigger_raw,
key_mask_raw            = 完整 16 位 key_mask
```

协议层不做死区、中心值、比例或扳机归一化。旧工程中的 `2048`、`1848`、`700`、
`3700` 不是厂商 SDK 常量，已从控制链路移除。

### 4.2 `key_mask`

厂商 SDK 将第三个 `int16` 字段作为 16 位位图：

| 位 | 语义 |
|---:|---|
| 0..4 | 基础键 `B0..B4`，active-low：`0=按下`、`1=松开` |
| 5 | 拨动开关：`1=ON`、`0=OFF` |
| 6..7 | 当前保留 |
| 8..12 | Plus/RF 机型扩展键 `X0..X4`，active-low |
| 13..15 | 当前保留 |

C++ 同时保存低、高字节，不把 bit5 伪装成旧的“模式字节”。当前 TIAGo 应用策略为：

- 运行：左右两侧 bit5 都为 ON，且基础键和已定义的扩展键均松开；
- 停止：左右两侧 bit5 都为 OFF；
- 掉线、数据过期、两侧状态不满足运行条件时停止发送新目标并保持/停止机器人。

这三条是本仓库的应用安全策略，不是额外声称厂商存在 `run_raw`/`exit_raw` 协议。

### 4.3 手柄校准

厂商 `Hand.GetCalibParams` 返回：

```text
jx_center, jx_max, jx_min,
jy_center, jy_max, jy_min,
trig_start, trig_max
```

遥操作层根据这些现场回读值做分段归一化：中心到最大值映射到 `+1`，中心到最小
值映射到 `-1`，扳机从 `trig_start` 到 `trig_max` 映射到 `[0,1]`。回中死区是本地
应用参数 `deadzone_raw`，不是厂商校准返回字段，默认应为 0 或由现场单独确认。

获取校准值：

```bash
python3 tools/qnbot_vendor_probe.py \
  --port /dev/exoskeleton \
  --show-topology \
  --show-calibration \
  --duration 2
```

把输出的 `Hand.GetCalibParams` 数值填入
`config/exoskeleton_tiago_teleop.yaml` 的左右手柄块，并将
`handset_calibration.verified` 改为 `true`。没有这些值时，`--confirm` 不会进入
实体控制。

## 5. 编码器与“人体姿态”重定向

### 5.1 厂商提供的内容

每侧 8 个编码器原始值按厂商 SDK 换算为弧度：

```text
encoder_rad = encoder_raw * (2 * pi / 16384)
```

换算后 C++ 的 `ExoskeletonState` 与 SDK 对齐：

```text
left_arm_joint_raw[8] / right_arm_joint_raw[8]
left_arm_joint_rad[8] / right_arm_joint_rad[8]
```

SDK 没有定义这些槽位的骨骼名称、左右镜像关系、零位、方向、人体姿态模型或
TIAGo 关节名称。因此不能从 SDK 单独推出“实际人体位姿”，也不能把一个旧的
7 元素 scale/offset 当成正确映射。

### 5.2 本仓库的应用层映射

TIAGo `Arm` 当前每侧接收 7 个模型关节目标。映射配置显式选择 8 个厂商槽位中的
7 个，然后应用：

```text
target_joint_rad[i] =
    vendor_encoder_rad[source_indices[i]] * scale[i] + offset_rad[i]
```

这一步必须逐轴活动外骨骼、确认顺序/方向/零位，并检查 TIAGo 模型限位。不能重复
应用 TIAGo `kinematics.yaml` 已经包含的方向或零偏。当前仓库提供的是中性占位值，
`retargeting.verified=false`，所以不会被实体遥操作接受。

如果未来需要真正的“人体姿态”而不是 7 个独立关节，还要在此层增加明确的骨骼
坐标系、基准姿态、人体段长/标定、正逆运动学或姿态重定向模型；厂商 SDK 本身不
提供这些内容。

## 6. 当前配置

### 6.1 串口配置

`config/exoskeleton.yaml` 使用：

```text
device       = /dev/exoskeleton
USB VID:PID  = 0x0483:0x5740
baudrate     = 2000000
poll timeout = 20 ms
stale        = 100 ms
frame size   = 131
```

`device` 为空或 `auto` 时才按 USB VID/PID 枚举；显式设备路径优先。当前 131 字节
值对应 SDK 的 `LEGACY_PAYLOAD_LEN_TORSO_EXTRA_IMU_QUAT=128`。

### 6.2 TIAGo 遥操作配置

`config/exoskeleton_tiago_teleop.yaml` 分为：

- `mode`：使用 SDK bit5，不再使用旧 raw 模式值；
- `handset_calibration`：必须来自 `Hand.GetCalibParams`；
- `retargeting`：8 槽到 TIAGo 7 关节的现场映射；
- `arm` / `gripper` / `base`：本体速度和限位前的应用策略；
- `safety`：单进程锁。

两个验证门必须都打开后才能实体跟随：

```yaml
handset_calibration:
  verified: true
retargeting:
  verified: true
```

本提交中的两个值都是 `false`，这是有意的安全状态，不表示映射已经完成。

## 7. 遥操作安全流程

实体程序的顺序是：

1. 加载并严格校验串口、校准和重定向配置；
2. 只读打开外骨骼，等待完整合法且未过期的 SDK legacy 帧；
3. 等待左右 bit5 均为 ON、按键松开、左手柄回中；
4. 读取 TIAGo 双臂和双夹爪反馈，检查首帧接管误差；
5. 对重定向后的关节、夹爪和底盘目标做本体限位检查；
6. 通过后才使能相关本体并启动 Executor；
7. 掉线、过期、key_mask 不安全、目标越限、Executor 故障或 Ctrl-C 时停止刷新
   新目标，并执行清理/禁用流程；
8. 运行期间左右 bit5 同时 OFF 时退出遥操作。

`--dry-run` 只检查配置，不打开串口、SocketCAN 或电机；实体控制必须显式传
`--confirm`。程序不应与厂商 SDK 探测器同时运行。

## 8. 联调顺序

### 8.1 先验证 SDK 和原始数据

```bash
python3 tools/qnbot_vendor_probe.py \
  --port /dev/exoskeleton \
  --show-topology \
  --show-calibration
```

确认版本、设备能力、legacy 快照、8 个编码器槽位和手柄校准值；必要时用厂商 CLI
执行 `hand.calib.wizard`，再用 `hand.calib.get` 回读。

### 8.2 再做 C++ 只读监测

```bash
cmake --build build --target exoskeleton_monitor -j2
./build/exoskeleton_monitor config/exoskeleton.yaml
```

逐轴活动外骨骼，记录每侧 8 个 raw/rad 槽位；同时确认 key_mask bit5、基础键、扩展
键、两个扳机和帧格式。此阶段不启动机器人 CAN。

### 8.3 最后做 TIAGo 联调

先只把两个验证门保留为 `false`，运行：

```bash
cmake --build build --target exoskeleton_tiago_teleop -j2
./build/exoskeleton_tiago_teleop --dry-run
```

现场完成手柄校准和逐轴重定向后，再分别审查配置、限位、首帧接管和急停，最后才在
可承托、低速、小范围条件下使用 `--confirm`。任何方向、零位、限位或停止行为未
确认时，不得直接打开双臂全范围跟随。

## 9. 自动验证覆盖

协议和流解码测试覆盖：

- SDK 51/91/131 三种帧长度和 `format_version`；
- little-endian `int16`、8 个编码器槽位及 SDK 弧度换算；
- 原始手柄轴、扳机、16 位 key_mask 和 active-low 语义；
- 帧头、帧尾、XOR 校验、拆包、粘包、噪声和失步恢复；
- IMU float、NaN、Inf 和无效四元数的数据质量标记；
- 不把 SDK 未定义的机器人关节语义混入协议层。

标准验证命令：

```bash
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build -j"$(nproc)"
cmake --build build --target exoskeleton_tiago_teleop -j2
ctest --test-dir build --output-on-failure
./build/exoskeleton_tiago_teleop --dry-run
```

## 10. 当前已知边界

- C++ 控制路径使用 SDK 已定义的 legacy 遥测流，不在实时周期里实现 QnTP 管理请求；
- 是否需要先用 QnTP 打开 legacy 流，按当前固件和现场流程由厂商工具确认；
- IMU 的物理单位、安装轴语义和 IMU 到本体姿态映射尚未由 SDK 定义；
- 编码器 8 槽到人体骨骼/TIAGo 关节的语义必须现场标定；
- 现有 TIAGo 工具控制 7 个 Arm 模型关节，不能据此声称已经完成通用人体姿态重定向；
- 只有 `handset_calibration.verified=true` 且 `retargeting.verified=true` 才允许实体
  控制，这两个门禁不能为了联调方便绕过。
